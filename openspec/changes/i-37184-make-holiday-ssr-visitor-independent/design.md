# Design

## Context

See proposal.md for motivation and the two delta specs for the behavior contract. This is an adaptation on branch `37184-prevent-cross-visitors-cache-leakage`, not a replacement of `archive/2026-11-03-i-37184-prevent-cross-visitors-cache-leakage`. The approved issue description is the requirements source; historical task text is not authority to retain country-specific SSR.

Original implementation context:

- `core/scripts/utils/page-cache-key.ts` splits clean render URLs from ignored query pairs; `ssr-response.ts` appends only the current request's stripped query when sending cached or fresh redirects. These protections already exist.
- `use-holiday-delivery-location.ts` evaluates persisted country, request cookie and US fallback immediately, including during SSR. The timeline widget uses that location to choose labels/options and has an immediate watcher that can emit Standard before browser data finishes loading.
- `persisted-customer-data/index.ts` dispatches the asynchronous `synchronize` action without awaiting it. The action reads shipping country after email/name/phone and commits it only after VAT/legacy-email reads; an unrelated delay or rejection can block country availability. An undefined country getter does not distinguish pending from absent/unreadable. There is no public readiness getter.
- `core/lib/store/storage.ts` already has an 800 ms `getItem()` callback fallback. Its instance-level `_cacheTimeouts.getItem` is cleared by the next read, so concurrent reads can cancel each other's callback fallback. Timeout does not settle the returned promise; that existing promise contract must remain unchanged. The user approved independent per-invocation timeout callbacks, not a shared promise-semantics change. Caller adapters still need the callback when backend readiness or the read remains pending, and can handle the same returned promise's rejection at their existing boundary.
- `use-customization-state-preservation.ts` already tracks restoration internally through `canUpdateState`, but returns only storage methods. Forms also call the immediate `useCustomizationsOptionsDefaultValue()` watcher. Gating only the timeline watcher would not protect every relevant defaulting path.
- The only production `registerOutputCacheVariation()` caller is `customization-system/server.ts`, for `detected_country`. The country feature accounts for the registry, marker/variant entries and extra tag. Other observed request-service cookie consumers use the existing A/B cookie dimension.

Product-page verification for this review: `pages/CustomizableProduct.vue:5–13` and `pages/PlushieProduct.vue:11–18` render the normal customization forms without overriding `customizationMode`; the gallery and wizard forms default to `ADD_TO_CART` (`form-with-images-gallery.vue:222–225`, `creation-wizard-form.vue:205–207`). `use-locked-customizations.ts:20–21,73–90` applies locks only in `CUSTOMIZE`; in the checked product-page mode it returns no locks and allows all option values through. The only explicit `CUSTOMIZE` override found is a separate page, outside this scenario. An `isLocked` product-data flag alone therefore does not establish an applied product-page lock. The existing characterization test explicitly passes `customizationMode: 'customize'` (`vertical-steps-restoration.spec.ts:559–583`, especially line 572), so it does not establish a normal product-page reproduction. The reported product-page lock's exact URL/SKU/input state is not confirmed; do not manufacture it by switching modes or changing lock scope.

The product page already has the selection, validation and price path needed for an eligible choice: `customization-option.vue:31–47` binds the existing field/validator, and the gallery form validates before its normal submit (`form-with-images-gallery.vue:494–504`). Its price is visible in the normal mode and comes from `useCustomizationsPrice()` (`:39–44,574–577`). The current field rules check required/max-count/email, not membership in eligible options (`use-customization-option-validation.ts:43–64`); a nonempty stale ID must not be assumed valid merely because required validation passes. Reuse this path with only the narrow eligibility/defaulting correction needed by the agreed case, rather than adding a parallel recovery or submission system.

## Goals / Non-Goals

**Goals:** Use explicit browser readiness at the existing data owners, preserve valid selections across asynchronous completion, and reduce output caching to safely shared responses plus existing store/query/A/B separation.

**Non-Goals:** No delivery eligibility or price changes; no new location service, cache plugin system, dependency scanner, automatic retry framework, global loading coordinator or general customization rewrite. Do not change the ignored-query policy, redirect destinations, supported query semantics, ticket status or archived files. This workflow makes planning artifacts only.

## Decisions

### 1. Keep Holiday SSR and the first browser render neutral

Update the existing `useHolidayDeliveryLocation()` rather than adding a parallel location abstraction. Expose unresolved location/readiness until both mounting and settlement of the browser shipping-country attempt permit resolution. Never read `detected_country` or choose a visitor location during SSR. Successful absence or an unreadable saved country permits detected-country/US fallback in the browser; failure must not leave loading indefinitely. Preserve any valid current selection and allow manual location changes after fallback. Normalize countries with the existing pure helper and retain manual override precedence.

Gate the Holiday widget's location selector, cards and location-dependent affordances behind readiness; show a small localized loading status with an appropriate busy/status announcement instead. The initial hydration tree remains neutral even if storage completed before mounting. Keep ordinary non-Holiday rendering unchanged. Shared API configuration can still include records for both locations in serialized state: it is visitor-selected content/state that must be absent, not public delivery configuration.

Rejected: US as a temporary displayed default (wrong content and premature selection changes), reading browser cookies during setup (hydration mismatch), and hiding only the label while still rendering actionable country-specific cards.

### 2. Settle the existing shipping-country read independently of unrelated fields

Use one minimal reactive shipping-country-settled flag/getter in `persisted-customer-data`, initially false for SSR/browser startup. Move the sole existing shipping-country read and its commit to the start of `synchronize`, before the unrelated sequential field reads. Publish its value, then settlement on success, absence or failure; do not wait for email/name/phone/VAT or legacy-email completion. Remove the old later country read/commit, reuse the storage handle, and retain the other fields' existing read/commit behavior. Catch storage acquisition/read failures at this owner and settle the flag so the composable can fall back; if module storage setup fails before dispatch, the same owner must expose settlement rather than blocking Holiday startup. Preserve existing diagnostic handling without logging saved values or swallowing unrelated field errors.

Consume the one shipping-country read through the narrow caller-owned callback adapter: its local readiness promise accepts the first callback success/fallback and handles synchronous failure or rejection from that same read. The adapter can finish on the existing timeout callback even while the driver's returned promise remains pending; it does not change or replace that shared promise's contract. Commit only after the accepted completion, so a late callback/result cannot overwrite fallback/manual choices or trigger a second reconciliation. Do not add duplicate reads or a separate caller timeout. Readiness means the caller's attempt has settled, not that all customer data loaded successfully.

In the existing shared `getItem()` implementation, replace the instance-wide read timeout with a timer owned by each invocation. Keep `CACHE_TIMEOUT` at 800 ms. Callback completion/cleanup clears only that call's timer; another read starting, finishing or timing out must neither cancel nor reset it. At its deadline, a hanging call delivers the existing local-cache/absent fallback through its optional callback. Guard that callback against duplicate delivery after timeout or late backend completion as necessary. Preserve the returned promise's existing contract: do not race it against a timeout, replace it with a timeout-settling wrapper or force its resolution/rejection on timeout in the shared driver; it may remain pending until backend work finishes and retain its existing eventual success/error behavior. Preserve existing success/fallback values, server/fast paths, diagnostics and local-cache population except for the approved same-key mutation guard below. Beyond that guard's hooks in `setItem()`/`removeItem()`, do not redesign write/delete behavior, `iterate()`, persistence thresholds or the storage API. Shared-driver scope is independent timeout callbacks, duplicate-callback guards and the narrowly approved cache-fill mutation guard, not unified callback/promise completion or error-status metadata to distinguish absent from unreadable drafts.

The second implementation review reproduced a late-read cache resurrection: after a read times out and the caller removes or writes the same key, the old backend read can still reach `getItem()`'s local-cache fill even though its callback is suppressed. Add a per-key mutation revision scoped to the existing cached entry (database/collection/key, including any driver instances sharing that local cache). Capture the revision at read invocation, before awaiting backend readiness/read; advance it when a same-key `setItem()` or `removeItem()` begins its local mutation, including memory-only/falsy writes and removal of a currently absent local key. Before applying a delayed backend result to local cache, require the captured revision still to match, in addition to existing fill conditions. Do not reset the revision on deletion while an old read can still complete. This invalidates only that stale cache-fill side effect: keep the in-flight read's existing returned-promise result, callback contract and backing-store behavior. A mutation to another key must not invalidate this read or change unrelated cache behavior. Use a small guard at the existing cache owner, not a generalized transaction/versioning service or another timer. These internal mutation revisions are not new draft-read failure metadata and must not be used to distinguish unreadable from absent drafts.

Expose existing saved-form restoration readiness read-only from `useCustomizationStatePreservation()`, retaining stale-attempt/product-key and pending-read guards. When the saved-draft result cannot distinguish an unreadable draft from absence, use the normal absent-draft path, including its normal `canUpdateState`/persistence behavior. Preserve valid current selections and do not merge nonexistent or partial draft data. Do not add a failure-specific write veto, storage-driver inspection, last-error check or new read-status metadata to distinguish those results. Reuse the sole existing saved-form read through a narrow callback adapter where readiness must finish on timeout, without requiring the driver's promise to settle or adding a caller timer. For forms without saved restoration, no extra wait is needed. Pass readiness through existing form → customization-option → widget props; no EventBus protocol or global readiness service is needed. Country fallback and manual location change must not wait on unrelated fields or an ambiguous empty draft result.

Keep required draft removal ordered at its existing owner: capture the draft key, acquire the existing mutex, await the real removal, then release the mutex and let only the current restoration attempt advance readiness through its existing flow. Handle/log a rejected removal and release the mutex in `finally`, so rejection does not leave that UI gate pending or skip the existing unavailable-draft flow. Do not race removal against a timeout, detach it or mark readiness complete while the delete is still outstanding; it could otherwise finish after a new draft has been saved and delete the new data. The user explicitly accepts that a delete which never settles can keep restoration/the widget loading and persistence gated. This is a pending-delete exception to read-fallback readiness, not a new failure classifier or write veto after an ambiguous read. Country resolution remains independent, but does not bypass required-removal ordering. No new removal timer, retry or general concurrency redesign is authorized.

This follows the user-approved decision recorded in issue #37184, note 232465: ambiguous saved-draft absence permits normal saving, accepting that an unreadable draft may be overwritten. Do not trigger a special write solely to handle the ambiguous result; ordinary absent-draft defaults and subsequent saving remain allowed. The earlier blanket prohibition on writes after an ambiguous failed read is superseded, while writes/reconciliation remain gated during loading and valid current selections remain protected.

Rejected: whole-`synchronize` success as readiness (unrelated reads can block country), a new parallel/duplicate storage load (unnecessary), keeping the instance-wide timer (caller adapters cannot recover a cancelled callback), changing the shared returned promise to settle on timeout (not authorized), promise-only readiness without a callback adapter (may stay pending after timeout), readiness inferred from a nonempty country (never ready for first-time visitors), mount alone (storage is asynchronous), and a new retry/state-machine framework (not required by the approved fallback).

### 3. Reconcile only against a ready set of options

Wait for location, restoration and option readiness; a temporarily empty list must not invalidate a selection. Preserve a still-valid selection, including a value shared across countries. Ordinary empty/invalid values retain existing Standard defaulting, except that a previously locked Holiday value unavailable on the product page needs the customer's explicit eligible choice.

Reuse the existing selected value, eligible option list and field/form validation. Do not auto-select Standard, including when it is the sole eligible choice, for that previously locked invalid value. The existing submission must reject an unchosen/ineligible value; the current required-only rule is not evidence that it already does. Keep valid locks and other locking rules, without globally changing `isLocked` or enabling `CUSTOMIZE` on product pages. No new recovery object, persisted flag, parallel submit gate or generalized validation/lock service is required by this proposal. The source of a genuinely applied product-page lock remains a factual uncertainty; verify that input before changing any lock implementation, and do not substitute a different flow to claim reproduction.

Keep normal option prices and the product total visible, using the existing price calculation for the eligible chosen value. The selected ID, displayed price and normal submission must agree. Do not hide the price by changing modes or invent a separate pricing baseline. Reuse the existing readiness and draft-preservation guards; non-Holiday choices, valid locks and other flows remain unchanged.

Rejected: removing reconciliation entirely (breaks genuinely invalid selections), unconditionally selecting Standard on mount (loses upgrades), and changing all customization defaulting semantics (unrelated behavior).

### 4. Remove country variation machinery, retain the cheap conservative guard

Remove the country server registration and the registry/marker/variant functionality whose only production consumer it was. Simplify `output-cache.ts` and `output-cache-types.ts` to response entries under the existing encoded store/query/A/B key. Remove the country-only invalidation tag from `config/local.json.template`; retain page tags, `redirect`, wildcard invalidation, cache TTL and existing configuration flags. No new flags or dimensions are added.

Keep per-render cookie-name recording at the existing request-services boundary and classify non-A/B reads as `no-cache`, including absent/repeated reads and late hooks/template reads. Reuse the existing preparation boundary and warning deduplication; shrink the existing helper or inline the small check rather than building a new policy interface. This is inexpensive protection already wired and tested; it is not a claim to detect raw cookie access or prove all future SSR output safe. It prevents storing observed cookie-dependent output on fresh renders. The known Holiday path instead avoids visitor inputs entirely, so it remains cacheable.

Rejected: retaining an unused extensible registry or registering more speculative dimensions (no current consumers), bypassing caching for every cookie-bearing request (would discard safe sharing), and deleting all cookie-read protection (would remove a low-cost existing safety check for late or accidental reads).

### 5. Preserve the implemented query and response boundaries

Do not redesign `splitPageCacheUrl()`, `appendStrippedQuery()`, the single clean-URL navigation, route/previous-route serialization or recorded application redirects. Keep current destination query precedence, original encoding, repeated/blank ignored pairs, fragment handling and supported client query restoration. Router forwarding/inherited/explicit-query redirects and applicable URL-rewrite/other recorded paths remain covered. Also retain sent-response guards, detached cache-write failure logging and cleanup/error containment.

Adapt variation-specific fixture expectations rather than replacing the existing synthetic request harness or broadening implementation scope. Country-independent redirects still share; an unexpected non-A/B cookie read forbids caching rather than creating a variant. Keep current store/A/B key encoding even after removing country suffixes.

### 6. Verify the actual widget lifecycle and reuse cross-request tests

Extend `holiday-delivery-country.spec.ts` to exercise mounted readiness, delayed shipping data, successful absence, unreadable-country fallback to detected country/US, persisted-country precedence and manual override after fallback. At the action/storage boundary use deferred unrelated field reads to prove country success/failure settles first and each attempt issues one shipping-country read. Cover synchronous throws, rejected driver readiness, resolved-empty results, timeout with the driver promise still pending but the caller-owned readiness adapter settled, and late callback/result ignored by that adapter after fallback.

Add a focused real shared-driver suite at `core/lib/store/test/unit/storage.spec.ts`, with fake timers and a stubbed backing store rather than a mock replacement of `getItem()`. Start two hanging callback reads on the same instance at staggered times and assert each callback receives its existing fallback at its own unchanged 800 ms deadline, with no cancellation/reset; cover hangs in backend readiness versus the read itself and a concurrent promise-only read that cannot cancel another read's callback. Complete one read early and verify only its timer is cleared while the other callback still times out. Verify returned driver promises remain pending on timeout for hanging backend work, retain existing eventual success/error behavior after late backend completion, and do not cause a second callback; observe rejections in tests without imposing new shared rejection semantics. Retain success, empty/error fallback, local-cache/SSR fast-path and existing single-read regression coverage. Verify caller-owned adapters separately complete readiness from the callback without requiring shared promise settlement. These tests belong to task 1.4 and do not broaden the driver's promise contract.

For the new mutation-guard work, extend that actual-driver suite with `read → timeout → remove(key) → late old result → reread(key)` and `read → timeout → set(key, newValue) → late old result → reread(key)`. Use a backing-store fixture whose current value follows the completed mutation, and verify the late read does not resurrect removed data or displace the new cached value; the original read's promise may still return its original result under the unchanged contract. Include an allowed falsy/memory-only write so the regression cannot pass solely because the old truthy-cache check already blocked a fill. Add controls where another key is mutated and where there is no intervening mutation, proving ordinary late fills and unrelated entries retain existing behavior. Keep callback/800 ms/promise-contract regressions intact. Do not replace them with a policy mock that bypasses real cache population.

Add a focused timeline-widget suite alongside the component, using the repository's Vue 2 SSR/hydration support: render neutral HTML, hydrate it with delayed browser data, then inspect content and emitted selection changes. Exercise saved Rush restoration before/after country completion, storage-failure/timeout completion, no intermediate Standard/persistence write while pending, manual location change after fallback, later valid/invalid location changes, shared SKUs, regular mode and desktop/mobile markup. Test an ambiguous empty draft result through the same absent-draft path: readiness completes, a valid current Rush remains selected, an actually empty selection can default normally, and subsequent ordinary saving is allowed even if it overwrites an unreadable draft. Do not add driver/error-metadata probes or assert a permanent write veto after settlement.

Extend the existing product-page form/widget tests in the actual `ADD_TO_CART` context; do not create a new integration framework or force `CUSTOMIZE` to fabricate a product-page lock. Cover readiness, eligible explicit choice without automatic Standard, visible normal price/total, invalid-value rejection through the existing validation path, valid-selection/other-lock controls and location changes. If the reported lock cannot be reproduced from actual product-page inputs, record the missing URL/SKU/state and stop lock-specific implementation rather than introduce a new locking flow. The desired conditional choice contract remains unchanged by that missing reproduction.

At the draft-restoration boundary, hold a required removal pending and assert readiness/new saving remains gated and no later save overtakes it. Resolve the delete and verify the existing flow can proceed; reject it and verify error containment, mutex release and current-attempt readiness without losing valid current selections. With a never-settling delete, assert the explicitly accepted pending/loading state persists rather than introducing a timer to force progress. Retain stale-restoration and captured-key tests so an old completion cannot release a newer product's gate.

Replace country-variant expectations in `output-cache-country.spec.ts` with a neutral Holiday response miss/hit test that uses the actual widget render/composable path, not only a synthetic cookie-to-label function. Reuse the in-memory TTL/tag cache and all existing redirect, HTML-state, isolation and response-ownership suites. Assert the entire shared HTML/state is visitor-independent and contains no synthetic query values; public identical API delivery records are not a leak. Verify no Holiday SSR country-cookie read and one shared entry across cookie values. Keep unexpected-cookie tests as no-write controls, not fabricated successful hits.

## Risks / Trade-offs

- Holiday location content appears after browser readiness instead of first paint → This is the approved trade-off; keep a neutral accessible loading status with no false promises or clickable options.
- Mount can precede storage and saved-form restoration → Gate both relevant owners and test both completion orders with emitted-event and persistence spies.
- A storage failure, concurrent read or unrelated sequential field delay could strand Holiday loading → Complete caller readiness from the sole read's callback/rejection adapter before unrelated reads, and give each shared invocation its existing-duration timeout callback. Preserve the driver's returned promise contract, resolve detected country/US and expose manual change; do not add duplicate reads or a separate caller timer.
- A late storage result or ambiguous saved-form result could replace a valid current selection → Accept read completion once, keep stale-restoration/pending guards, and verify valid Rush preservation; ambiguity is not evidence that the current selection is invalid.
- A test can manufacture a lock the product page does not apply → Use the actual product-page mode/inputs. The checked lock helper already allows alternatives in `ADD_TO_CART`; the reported lock's provenance is unconfirmed and must not justify a new lock/recovery system.
- Suppressing a late callback alone still lets an old read repopulate cache after a same-key mutation → Guard that cache-fill side effect with the captured per-key mutation revision, preserving returned read results and unrelated-key/no-mutation behavior.
- A never-settling required delete can leave the widget loading → This residual risk is explicitly accepted to prevent a late delete of newly saved data. Keep the delete ordered with the existing mutex and no timeout/detachment; a rejected delete is settled and must release the current UI flow rather than strand it.
- An ambiguous absent-draft result may really be an unreadable draft, and normal saving may overwrite it → This risk is explicitly accepted in issue #37184 note 232465. Follow ordinary absent-draft persistence without new driver/metadata checks or a failure-specific write veto.
- Browser-only gating could mask a parent default watcher → Gate the identified Holiday default paths, and verify selected values and storage through a real form restoration fixture.
- Existing tests encode the archived variant policy → Replace those expectations explicitly; preserve query/redirect, tags, no-cache and response-ownership assertions rather than deleting coverage indiscriminately.
- Old caches contain country-dependent entries → Use a fresh build namespace and never mix incompatible releases under one prefix.

## Migration Plan

Implementation follows this new active change. Do not edit archived artifacts; leave canonical specifications unchanged until the normal later sync/archive workflow, where the country-first-paint requirement is removed and replaced by these deltas. The canonical purpose's old first-paint wording must be reconciled during that later sync, not by rewriting archived history in this proposal.

Build/deployment already generates a fresh `core/build/cache-version.json` prefix used by `cache-instance.ts`; use a fresh prefix for the adapted release rather than reading old country markers/responses. No live invalidation or Redis operation is part of this proposal. Verify neutral cache reuse and current-browser query flows with synthetic values before rollout. A rollback requires its own fresh build prefix; returning to the old release restores country-specific SSR and is not the approved end state.

The approved decisions remain: neutral SSR, browser-country fallback, readiness and valid-selection preservation, explicit eligible choice for a previously locked invalid Holiday value on the product page, ordinary defaults elsewhere, normal persistence after ambiguous draft absence, the narrow shared-storage fixes and ordered draft removal with its accepted never-settling-delete risk. The factual gap is the reported product-page lock: the checked product-page callers use a mode in which the lock helper does not apply locks. Do not invent a reproduction or broaden scope to bridge that gap. The user declined issue updates; do not change the issue or its status.
