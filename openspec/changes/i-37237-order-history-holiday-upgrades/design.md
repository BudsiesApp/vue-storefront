# Design

## Context

See `proposal.md` for the two operator-requested fixes and `specs/production-time-option-presentation/spec.md` for the contract. Requirements R7–R9/G4 belong to this new storefront change. The deployed Magento change `i-37237-holiday-period-alteration-bundles` and merged PR #514 remain history, not branches to reopen.

Observed implementation:

- App `src/modules/customization-system/helpers/update-product-production-time-customization-data.ts` reads Rush add-ons from Vuex, collapses ordinary/card-list records by SKU, replaces option labels, and prepends synthetic Standard. Its `isHolidayPeriod` switch belongs to the timeline widget and is absent on the five alteration bundles. The no-add-ons path currently removes the customization by mutating the supplied product.
- App `src/modules/budsies/factories/rush-addon.factory.ts` currently uses `Boolean(data.is_domestic)`; `RushAddon.isDomestic` defaults to false. Missing ordinary metadata and an explicit international Holiday record therefore become indistinguishable in client state.
- Magento `VueStorefrontIndexer/Model/Indexer/Action/RushUpgrade.php` emits `is_domestic` only when the prepared option carries destination metadata, including false; ordinary records omit it. Holiday Standard records remain destination-tagged even when no Rush survives. No new backend flag is needed.
- `Order.shipping_address.country_id` already exists in `src/modules/orders-history/types/`, but the frontend currently overstates address presence: Magento `OrderHistory/Api/Data/HistoryOrderInterface::getShippingAddress()` is nullable and its provider returns null when absent. Magento `Sales/Service/LocationDetector::isOrderDomestic()` returns false for a missing address/country, otherwise comparing shipping country with `shipping/origin/country_id` for the order's store. A bounded local config read returned default `US` with no scoped override; the storefront's existing convention is US/international. Use the exact `US` country as domestic and other/missing countries as international, not the visitor-country fallback helper which defaults absence to US.
- Theme `helpers/use-alteration-products-loader.ts` prepares a dictionary by order item but flattens away parent orders; `helpers/use-order-item-alteration-product-loader.ts` receives `order` but does not use it. Both already load associated-product prices and Rush data through existing Vuex actions.
- Theme `helpers/use-alteration-product-customizations.ts::optionValuesFilter()` removes synthetic Standard and already-purchased values. Its `customizationsFilter()` returns early when no purchased value exists; `alteration-product-form.vue` can therefore render a Production Time heading even though the child receives no selectable values.
- The relevant loader/form/helper blobs are identical on the fetched theme branches. The PM's dev-catalog evidence and updated R9 limit affected storefronts to Petsies, Budsies and Education: #830/#831 are assigned to the Budsies website, #832–#834 to Petsies, and Education uses Budsies' `default` store. Waggables and Bulk Orders sell no post-purchase alteration bundles. The established release convention nevertheless propagates released changes to their store branches by merging `petsies-theme`, to limit future conflicts; it does not require feature copies, additional PRs or deployments there.

Canonical context: existing `production-time-option-presentation` requirements describe the product-page timeline/location toggle, not order-owned cards-list filtering. This delta adds that scoped contract without changing those requirements. `order-history-alteration-product-pricing` and archived `i-36911-fix-sneak-peek-price` require both loaders' price-prefetch path to remain. Archived `i-37022-update-holiday-period-options-display` and `i-37184-make-holiday-ssr-visitor-independent` explain why product-page location readiness and shared-SKU variants must stay intact. The Magento archive records the formerly accepted shared-list limitation; this follow-up supersedes that limitation in the storefront, not the historical archive.

## Goals / Non-Goals

**Goals:** Fix the order-owned projection before SKU collapse, and final form visibility after option filtering. Reuse the existing destination records, order response, form filters and cart flow. One app-owned OpenSpec change coordinates both repositories; do not duplicate its behavior contract in the theme's unrelated spec root.

**Non-Goals:** No new backend/API data, Magento changes, client cutoff calculation, widget switch, visitor-country lookup, slot-counter enforcement, new index trigger, payment/cache-module change, dependencies, schema, checkout validation, replacement message or order-address mutation. No per-brand feature branches/copied patches/propagation PRs, no implementation-owned release merges, and no required Waggables or Bulk Orders deployment. Leave the existing destination-independent no-add-ons removal behavior unchanged. An open page crossing a cutoff remains the accepted O11 case. No production memberships or dates are changed by code.

## Decisions

### 1. Preserve existing destination metadata instead of inventing a Holiday detector

In app `src/modules/budsies/models/rush-addon-api-response.interface.ts`, type `is_domestic` as optional and compatible with the backend's boolean representation (and the numeric representation already handled). Preserve its absence as `undefined` in `RushAddon.isDomestic` and the factory rather than coercing it to false. Explicit false/zero must still become false; true/one becomes true. Keep other fields and constructor positions compatible.

The canonical producer already supplies the necessary discriminator: ordinary records are untagged, Holiday records are tagged. Do not infer Holiday membership from labels, SKU prefixes, duplicate records, current dates, `isInTimeForChristmas` truthiness, or `displayWidgetOptions.isHolidayPeriod`. This preserves false international records and ordinary data without another flag or API request. Existing timeline code filters tagged records only within Holiday widget mode and remains unchanged.

Cost: rung 4, a small extension around existing rung-2 contracts. Configuration alone (rung 1) either keeps the defect or enables a timeline toggle the PM excludes. Building another cutoff engine or changing Magento is unnecessary and out of scope.

### 2. Add an optional order-destination projection to existing preparation

Extend the preparation helper's existing options with an optional `isDomestic?: boolean`. When supplied, retain untagged ordinary add-ons as before and retain tagged Holiday add-ons only when their destination equals that value. Apply this before Standard lookup and SKU-dictionary construction. Check optionality by type/presence, not truthiness: international false is a supplied context. Callers without this option retain the current timeline/product-page path, including its location readiness, manual toggle and slot policy.

Do not set `isHolidayPeriod` merely to obtain filtering: that also changes presentation and enforces slots, contrary to O7/O8. The cards-list path continues to use its existing labels and does not acquire the timeline's zero-slot exclusion. Preserve original option-value IDs, SKUs, prices and bundle selection linkage; metadata chooses which existing value is offered, not another product to buy.

Leave `removeProductionTimeCustomizationFromProduct()` and the existing empty-global-add-ons check unchanged. That removal is destination-independent and changing its mutation would alter product-page behavior outside R7. For a Holiday member, Standard records exist for both destinations, so the new destination filter does not turn the non-empty global list into an empty one. The normal update path already returns new product/option objects; reuse it for each order-specific projection and keep the two-orders/shared-bundle isolation test. No immutability rewrite, raw-product mutation test, catalog cloning or per-order Vuex cache is needed.

Alternative: filter only the rendered widget after SKU collapse. That is too late to recover the international record's identity/terms and would require wider component plumbing. Filtering the global Vuex getter would affect product pages and other orders. A separate preparation pipeline would duplicate existing Standard/label/identity logic.

### 3. Pass the owning order through both theme loaders

In `use-alteration-products-loader.ts`, keep the existing flattened SKU/load collection if useful, but construct `alterationProductByOrderItemId` by iterating each parent order and its items. For each prepared product pass `makeProductionTimeRequired: false` plus `isDomestic: order.shipping_address?.country_id === 'US'`. Prepare a projection per order item through the existing update path, even when SKUs match. Keep associated-product prefetch and Rush requests unchanged.

In `use-order-item-alteration-product-loader.ts`, use the existing `order` ref to pass the same optional-chain expression. Do not expose the prepared alteration product until its owning order is available; its existing undefined/loading form path already accommodates this. An available order with no shipping address is different from a not-yet-loaded order: classify the former as international immediately, without crashing or waiting for an address. Recompute from the product dictionary when the order or its shipping data changes and do not borrow context from the previous order. No persisted-country, cookie or browser-location fallback belongs here.

A pure shared classification helper is optional only if it reduces repeated code; the optional-chain equality check in each loader is enough. Update app `src/modules/orders-history/types/order.ts` so `shipping_address` permits absence and the API's explicit null (for example, `shipping_address?: OrderAddress | null`). Test null/absent address and missing country as international in both loaders, including one such order beside an ordinary domestic order in the list. This is contract fidelity backed by the nullable API and Magento's false result, not speculative handling; add no further address validation. The local and existing storefront US convention is the evidence for this scope; if release configuration reveals a non-US shipping origin, raise it to the PM under O12 before inventing another classifier or changing APIs.

### 4. Filter the empty customization at the existing alteration boundary

In theme `use-alteration-product-customizations.ts::customizationsFilter()`, before the early return for a missing purchased value, handle `OptionType.PRODUCTION_TIME`: require at least one available value that passes the same `optionValuesFilter()` already supplied to the form's value projection. Synthetic Standard and already-purchased values do not count. Use that existing filter instead of creating a second list of excluded IDs.

`alteration-product-form.vue` already renders headings/controls by iterating `filteredCustomizations`; omitting that customization removes the entire section. Leave other customization types, collapsed-view calculation, validation, Standard bookkeeping and add-to-cart handling alone. Do not hide only the child widget with CSS or alter `requiredCustomizationsFilter` globally. A local predicate fixes R8 at the owner and avoids changing unrelated required fields.

### 5. Use one companion PR pair and normal release propagation

Implement on exactly one app branch and one theme branch, both `37237-order-history-holiday-upgrades` from fetched `petsies-theme`, with one ready feature PR per repository into `petsies-theme`. Primary checkouts stay on those branches. The five unnecessary suffixed local refs created during planning are removed after verifying they remain at their original bases; no feature work is copied to brand-specific branches.

- App `BudsiesApp/vue-storefront`: `37237-order-history-holiday-upgrades` → `petsies-theme` (base `dd5d6b3ee116e2c675d28b52e5eb370f8941c82b`).
- Theme `BudsiesApp/vsf-capybara`: `37237-order-history-holiday-upgrades` → `petsies-theme` (base `9c8e7cb939ae6e52ea42a39a7b1257a99c23abb9`).
- CI-only dependencies, not feature repositories: `vsf-payment-braintree` stays on `optimuspro`; `vsf-cache-varnish-1` stays on `budsies`. No ticket branch or source changes there. VSF API continues passing through the existing destination records; Magento remains the deployed prerequisite.

App `.github/scripts/resolve-pr-ci-selection.js::resolveThemeBranches()` selects the same-ticket theme branch when its PR into `petsies-theme` is open. Publish that one theme companion PR alongside the app PR before relying on app CI; no per-brand CI pairings are needed. The `.github/workflows/test_vsf1.yml` pipeline runs lint, maintained tests and builds against the companion branch with payment unchanged. A default-theme green run without the companion PR is not evidence for the theme fix. Do not commit app submodule pointers or use the old Magento branch/PR. No CI edits are required.

The authoritative propagation rule is `budsies-vuestorefront-production-deployment`, **Release Rules**: merge feature PRs into `petsies-theme`, then propagate every released change to all store branches with `git merge`, including brands that do not display it. Never cherry-pick, copy patches, rebase or create PRs solely for propagation. The release owner performs dry-run merges and brand-specific compatibility review/adaptation: theme targets are `budsies-theme`, `budsies-education-theme`, `waggables-theme`, `bulkorders-theme`; the app target is `bulkorders-theme`. This necessary release preparation replaces the five extra feature branches/ports/PRs and their duplicate test/CI runs; it does not require deploying the two unaffected storefronts. Post-merge `petsies-theme` CI also runs the existing default theme matrix. Propagation and its checks belong to release preparation, not tracked implementation tasks or permission to merge in this spec stage.

## Risks / Trade-offs

- [The factory currently erases absent-versus-international metadata] → Retain missingness and test raw false, true, zero, one and omitted values through the factory and public preparation helper. Both cutoffs expired still leaves tagged Standard, so detection does not depend on a surviving Rush record.
- [A form left open crosses a cutoff] → Accepted O11: no timer or new server validation. Existing refresh supplies updated choices on the next load.
- [Order data arrives after cached product data] → The existing single-item undefined-product path waits for its own order before preparing a context-specific product; no default domestic guess or cross-order state is introduced.
- [Future stores use a non-US shipping origin] → Existing storefront conventions and the bounded dev config use US. Do not generalize this ticket with new config/API work; escalate under O12 if the actual release target differs.
- [Retiring the workaround before all affected storefronts ship reopens the old gap] → Keep it until the propagated app/theme combinations for Petsies, Budsies and Education are deployed and destination-specific verification passes. Waggables/Bulk Orders take propagation merges but their deployments are not prerequisites. Retire it only through the release operator steps below.

## Validation and tester handoff

Implementation checks belong with the code they protect:

- App factory/preparation tests under `src/modules/*/test/unit/`: optional metadata fidelity, destination filtering before SKU collapse, both mixed-cutoff directions, tagged Standard with no matching Rush, ordinary data with supplied context, callers without context, zero-slot cards-list preservation and unchanged IDs/prices. Retain the two-orders/shared-bundle destination-isolation test through the existing update path; do not add a raw-product immutability test or rewrite the destination-independent removal path. Scope new behavior with the optional context rather than changing product-page expectations.
- Theme loader/helper tests: exercise both loaders using a single shared bundle with US and international parent orders, late order availability in the single-item loader, and null/absent shipping address or missing country classifying international. Test the changed customization predicate directly for Standard-only, purchased-only and eligible values. Preserve associated-price prefetch behavior. The live tester verifies the rendered form and existing cart flow below; do not duplicate the predicate with a form test whose mocks decide its result.
- Run `docker compose exec -T app yarn test:unit --runInBand --runTestsByPath <focused paths>`, `yarn test:unit:maintained`, `yarn type-check`, focused ESLint and existing CI lint/build commands on the single companion app/theme feature pair. Run project tooling inside the documented UI container; do not run a second installation in a worktree. Do not port code or add per-brand feature checks. Release propagation dry-runs, brand adaptation and pushed-combination CI remain the release owner's responsibility under the deployment skill. E2E/live browser work belongs to the tester, not tracked implementation tasks.

Required live tester flows, using non-production fixtures and the normal Rush index refresh: (1) a Holiday bundle with one destination expired and the other in Rush Delivery, two orders sharing the bundle, and each order seeing only its own options; verify both list and single-item entry points across the pair; (2) both cutoffs expired, no Production Time heading, and another upgrade can still be added to the sandbox cart; (3) unchanged product-page destination toggle and one non-Holiday alteration regression. Use a representative affected brand for the full flow and cheap smoke checks of the other affected storefronts after normal propagation (Petsies, Budsies and Education only). Release-branch compatibility and CI checks still follow the deployment skill for all propagation targets; Waggables/Bulk Orders need no deployment or separate live alteration flow. Additional unchanged-phase and workaround-cleanup live checks are optional where fixtures already make them cheap.

## Migration Plan

No data migration, new index trigger or catalog/widget edit is required to deploy the code. The release owner follows `budsies-vuestorefront-production-deployment`: merge the one app PR and one theme PR into `petsies-theme`, dry-run and perform the normal propagation merges into all store branches listed in Decision 5, and adapt/review the affected behavior while preserving brand differences. Do not create separate feature copies or PRs for those merges. Deploy only the approved affected storefronts—Petsies, Budsies and Education—after the delivered Magento destination-record prerequisite; Waggables and Bulk Orders receive source propagation but need no deployment for this follow-up. The release owner must copy G4 instructions below into #37237's Deployment instructions while preserving useful historical notes. This spec does not update Redmine or authorize merges, propagation, deployment or production writes.

**G4 — retire the earlier-date workaround after release verification:**

1. The separate alteration group with both Rush cutoffs at the earlier date is no longer needed once the destination-aware storefront is deployed for Petsies, Budsies and Education and verified. Do not wait for a Waggables or Bulk Orders release. If it was never applied, leave memberships and dates unchanged.
2. In **Budsies → Holiday → Periods → Christmas 2026 → Product Groups**, inspect the actual separate group and intended main-product group; do not guess a new group ID or overwrite the main-product dates. The original mapping is #830 → Budsies #47, #831 → Selfies #46, #832/#833/#834 → Forevers + Golf Covers #48, unless the operator has intentionally reorganized it.
3. A product can belong to only one group in the period. If the separate group contains only the alteration bundles being moved, delete that separate group through the existing confirmed Admin Delete action first (do not try to save an empty group). Then add those bundles to their main-product group and save. If the separate group also contains unrelated members, remove only the moving alteration bundles, save it with its remaining members, and preserve that group. Do not delete unrelated members or groups.
4. Preserve the main-product group's existing dates exactly as displayed in Admin; the returning bundles now use those normal destination-specific dates. Let the existing group-save/delete refreshes finish and confirm the restored membership and order-destination choices. No manual new trigger, widget switch or attribute edit is part of this procedure.

Operator actions are separate approved production changes. During a delete-then-add move there is a brief unassigned interval and normal asynchronous refresh; complete the move as one operator procedure and verify its final state rather than promising atomic membership transfer the Admin does not provide.

Rollback requires the ordinary release owner's approval and matching app/theme versions. Reverting the frontend restores the old shared-list limitation. If the workaround has already been retired, the release owner must decide whether to reapply it through the existing Admin procedure before/alongside rollback; code rollback does not automatically edit memberships or dates.
